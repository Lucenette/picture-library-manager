# 用本机编辑器打开脚本

**状态**：待评审
**关联**：[script-management.md](../design/script-management.md)（脚本正文落盘与草稿机制）

---

## 1. 背景

1. **脚本正文已经是磁盘上的真实文件**：`~/.plmanager/scripts/<uuid>.js`（开发态 `dist/.plmanager/scripts/`），库里只留索引（名称、路径、类型、分组）。既然它就是一个普通文件，"用我自己的编辑器打开它"是顺理成章的诉求，但界面上没有任何入口。
2. **内置编辑器只是够用**：Monaco 提供语法高亮、类型检测与改动色条，而使用者自己的插件、快捷键、多光标与格式化习惯都在自己的编辑器里；现在想用它们只能自己去数据目录翻文件——`<uuid>.js` 这种文件名不告诉人哪一份是哪个脚本。
3. **外部改动天然生效，缺的只是"打开"这一步**：每次调用脚本都会重新读盘（按路径 + mtime + 大小判断要不要重读），所以外部编辑器改完保存，下一次扫描 / 选图就用新内容，不需要"同步回来"。
4. **打开哪个编辑器要探测，不能猜**：同一台机器上可能装了好几种编辑器，各自的启动方式与可执行文件位置都不同（`code <file>`、`idea <file>`、macOS 的 `open -a`、Windows 的注册表登记），猜错的表现是"点了没反应"或打开了别的东西。
5. **现成参考**：dsh 的 open-in-app 已经走通这条路——一张编译期表 + 每条"定位器"都必须验证可执行文件真的存在（注册表 `App Paths` / 卸载记录、`/Applications` 扫描、PATH 与 Toolbox 脚本）。本项目只需一张小得多的表。

## 2. 目标与非目标

**目标**

1. 脚本管理页有「用其他编辑器打开」的入口，默认编辑器在会话内记住。
2. 只列出这台机器上**确实装了的**编辑器：每一项都要验证可执行文件存在，不做"启动一次试试看"。
3. 打开的是**磁盘上的那份脚本文件**；打不开要看见原因（界面提示 + 日志一条 error），不静默失败。

**非目标**

- 不做外部编辑器的安装、升级与配置管理；
- 不做"外部改了正文，内置编辑器里那一版自动跟着变"——重新打开该脚本时本来就会重新读盘；
- 不改脚本的存储方式与草稿机制。

## 3. 设计

### 3.1 探测：一张编译期小表 + 每条都要验证

- 表里每个编辑器声明**按平台**的定位器链，取第一个验证成功的：
  - Windows：注册表 `App Paths`（`Code.exe`、`idea64.exe`…）→ 卸载记录的 `InstallLocation` / `DisplayIcon` → 常见安装路径（`%LOCALAPPDATA%\Programs\...`、`%ProgramFiles%\...`）；JetBrains 系额外扫 `%ProgramFiles%\JetBrains\<产品><版本>` 取最新版本目录（数字感知排序，`2024.1.10` 排在 `2024.1.9` 前）。
  - macOS：`/Applications` 与 `~/Applications` 里按 bundle 名找（`Visual Studio Code.app`、`IntelliJ IDEA.app`…）；只查已知路径，不做 Launch Services 查询。
  - Linux：PATH 上的命令名（`code`、`idea`…）与 `~/.local/share/JetBrains/Toolbox/scripts/<cli>`。
- **每条都要落地验证**（目标文件真的存在）才算数；Windows 的注册表整趟只查一次，不按编辑器重复查。

### 3.2 打开：detached、不过 shell、argv 直接给文件路径

- `spawn(命令, [脚本文件路径], { detached: true, stdio: 'ignore' })`，不拼 shell 字符串；每个条目自带参数模板（JetBrains 与 VS Code 系列直接给路径，macOS 走 `open -a "<App>" <文件>`）。
- 子进程用**抹掉凭据**的环境（不带应用的 `*KEY*` / `*SECRET*`），并且不因编辑器前台常驻而等它退出：只留一个很短的观察窗口抓"立刻失败"。

### 3.3 入口与记忆

- 脚本管理页的右键菜单加一项「用其他编辑器打开」，与「重命名 / 放弃修改 / 删除 / 恢复默认」并列，子菜单列出探测结果。
- 选中项在会话内记住并排在子菜单最前（是否跨启动持久化见待决事项 3）。

## 5. 风险

| 风险 | 应对 |
|---|---|
| 探测误报：注册表里有登记但程序已被删 | 每条都验证目标文件存在；打开失败时报错，并给"手动指定"的退路 |
| 打包后进程的 PATH 与终端不同（macOS / Linux 的 `code` 常不在 GUI 进程的 PATH 里） | 优先注册表、bundle、Toolbox 脚本这些不依赖 PATH 的定位器，PATH 只作最后补充 |
| 各编辑器命令行约定不一 | 表里每个条目自带参数模板 |
| 外部改坏正文，使用者以为是应用的问题 | 报错信息里带上脚本文件路径；文档补一句"正文就是那个文件" |
| macOS 的 bundle 改名或挪到 `/Applications`、`~/Applications` 之外就探测不到 | 承认这个边界（与 dsh 的 open-in-app 同样的已知限制），用手动指定兜底 |

## 6. 验证方法

1. 纯逻辑：注册表 dump 的解析、版本目录排序（`2024.1.10` > `2024.1.9`）、定位器链短路——都能在沙箱里用固定输入跑断言。
2. 人工冒烟：Windows / macOS / Linux 各确认——装了的编辑器出现在列表里、点开真的打开当前脚本文件、外部保存后应用下一次调用读到新内容、卸载后列表里不再出现。

## 7. 待决事项

| # | 事项 | 倾向 |
|---|---|---|
| 1 | 打开的是正式脚本文件还是草稿 | 正式文件（`scripts/` 下那份）；草稿是编辑器的会话状态，不落成可打开的产物 |
| 2 | 有未保存改动时要不要先提示 / 保存 | 先提示「外部打开的是上次保存的那一版」，不自动保存 |
| 3 | 默认编辑器是否跨启动持久化 | 先会话内记住；要持久化再加设置表或字段 |
| 4 | 探测漏掉的编辑器怎么办 | 子菜单给一个「其他…」手动选可执行文件，选过之后会话内记住 |
