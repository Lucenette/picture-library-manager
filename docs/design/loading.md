# 加载服务：启动任务的登记与调度

**状态**：现行架构
**最后更新**：2026-09-27

---

## 1. 背景

1. **启动阶段要做的事散在 `bootstrap()` 里，顺序只写在注释里。** 建窗口、开库、升级、注册其余通道、预热浮窗挤在一个函数里，谁先谁后靠读代码维持；「升级终态发出之后到所有通道注册完成之间不许有 `await`」这条不变量更是只能靠评审盯着（见 [ups.md](./ups.md) 第 4 节风险 6）。
2. **加了预热之后这个问题变尖锐。** 脚本管理页把整个 Monaco 连同两个 worker 一起吞进自己的 chunk：`esm/vs` 源码 25.7 MB / 1511 个文件，其中 worker 侧的 `typescriptServices.js` 8.86 MB、`lib.js` 3.14 MB，`?worker&inline` 还要把它们 base64 内联（体积约为原来的 4/3）。第一次点进那一页要现场下载并求值，使用者的实测反馈是「首次加载脚本管理页时间很长」。想在启动阶段把它做掉，就需要一个能表达「什么时候跑、跟谁并行、失败算不算数」的载体。
3. **升级原本直接对着加载页发消息**（进度、快照、退出三条通道都叫 `ups:*`），加载页因此认识「数据库升级」这个具体业务；换一个启动任务就得再开一套通道。
4. 结论：把「启动阶段的任务」抽成加载服务——任务登记进来，调度、状态、跨进程下发都归它，升级与预热只是它的两项任务。

## 2. 组成：两块代码，一份任务表

| 位置 | 职责 |
|---|---|
| `src/main/loading/index.ts` | 模块出口：登记、启动、等待退出与状态类型 |
| `src/main/loading/registry.ts` | 任务表与调度：`registerLoadTask()` / `startLoading()` |
| `src/main/loading/progress.ts` | 状态与通道：快照、进度推送、退出、渲染进程任务的下发与回执 |
| `src/renderer/loading/index.ts` | 渲染进程那一半：状态引用、按 id 认领任务、回执、报告就绪 |
| `src/renderer/views/startup/LoadingPage.vue` | 加载页：只读状态画界面 |

任务只在主进程登记（`src/main/index.ts` 的 `bootstrap()` 里三行），渲染进程只声明「自己会跑哪些 id」：

```
主进程                                          渲染进程
createMain('/loading')
initLoadingIpc()                                 entries/main.ts
initDatabase()                                     registerRendererTask('editor', …)
registerLoadTask(数据库升级 / 初始化 / 编辑器预热)   initRendererLoading() ─┐
startLoading()                                                          │ 先订阅，
  ├─ essential：按登记顺序 await ─ load:progress ─► loadState ─► 加载页  │ 再 invoke
  └─ warmup：立刻起跑，不等它                                           │ (load:state)
       └─ target=renderer ─ load:task ─► 查表 → 跑 → load:taskDone ◄────┘ 就是就绪信号
```

## 3. 调度：登记时给两个标记

| 标记 | 取值 | 含义 |
|---|---|---|
| `kind` | `essential` | 必须跑完才放行主界面：加载页等它、显示它的进展；抛错即整轮失败 |
| | `warmup` | 与必须的任务并行，跑完不放行、失败只记一条 `console.warn` |
| `target` | `main` | 加载服务直接跑 |
| | `renderer` | 下发到渲染进程、等回执 |

- **「必须」的任务按登记顺序串行。** 启动顺序是硬的（先开库、再升级、最后注册其余通道），不能为了并发把它们打乱。
- **预热任务在 `startLoading()` 一开头就全部起跑**，与「必须」的任务并行；它们不参与放行判定，也不参与成败判定。于是升级跑多久就预热多久，而没有升级要跑时它退化成后台预热，不会让启动多等一秒。
- **失败只由「必须」的任务定义**：它抛出的错误成为加载页上的 `error`，`startLoading()` 返回 `false`，调用方等用户点「退出」再收摊。预热任务失败不改变终态——它只是没预热上，下次进那一页慢一点，日志里有记录。

## 4. 状态只有一个来源

- **状态在主进程**：任务名、终态与错误由加载服务写；任务通过 `report({ step, done, total, percent, note })` 只补自己这一步的进展（`note` 是失败时的附注，升级用它带备份路径）。
- **没有进展就不推**：进入一个「必须」的任务只记下任务名、不推送（`beginLoadTask()`），任务报了第一条进展才推送。否则正常启动——根本没有要加载的东西——也会闪一下加载页。
- **终态由加载服务公布**：`finishLoad('succeeded')` 在所有「必须」任务跑完之后才发出，加载页只认这一条来切主界面。
- **加载页只读**：`loadState` 是渲染进程的模块级 `ref`，所以推送比页面挂载更早也不丢（先订阅，再 `invoke(load:state)` 取一次快照）。`status` 不是 `succeeded` 才画界面，`failed` 时多画错误、附注与「退出」。

## 5. 时序不变量为什么不再需要人守

原先是：**升级终态发出之后到所有通道注册完成之间不许有 `await`**，否则渲染进程可能在通道还没注册时就回主界面。

现在升级是「必须」的任务之一，其余初始化是紧跟其后的另一个「必须」任务，终态在两者都跑完之后才公布——**加载页不可能在通道注册完成之前收到终态**。往任务表里加任务不会破坏它；绕过任务表、在 `startLoading()` 之后直接 `await` 做事才会。

## 6. 跨进程：就绪、下发与回执

- 渲染进程入口调 `initRendererLoading()`：先挂上 `load:progress` 与 `load:task` 的监听，再 `invoke(load:state)`——主进程收到这次调用就知道可以下发了（既取快照，又是就绪信号）。
- 下发用 `requestId` 配对：`load:task` 带 `{ requestId, id }`，渲染进程跑完发 `load:taskDone` 带 `{ requestId, error }`（空串为成功）。
- **主窗口关掉就没人回执了**：`closed` 事件会把等就绪的、等回执的统统按失败唤醒，启动流程不会被一个永远不回来的回执挂住。
- 渲染进程不认识某个 id 时，回执里写明「不认识的加载任务」，主进程按普通失败处理。

## 7. 改动时的检查点

- 新增启动步骤就 `registerLoadTask()` 登记，别在 `startLoading()` 之后直接写同步代码或 `await`——那会重新引入第 5 节的问题。
- 任务的实现（主进程）与认领（渲染进程）用同一个 id：常量加在 `common/ipcChannels.ts` 的 `LOAD_TASK` 里，两边都从这里取。
- 给任务加新的进展字段时，同步改 `common/types.ts` 的 `LoadProgress`、`progress.ts` 的 `LoadTaskPatch` 与加载页的展示。
- 预热任务不许阻塞启动：它要么放在渲染进程的空闲时刻跑（见 `entries/main.ts` 的 `warmUpEditor()`），要么是主进程里明确「可以慢」的活。

## 8. 已知取舍

| 取舍 | 代价 |
|---|---|
| 加载页只画加载服务公布的一种状态，不再是「升级页」 | 升级特有的措辞（备份路径、接着这一条继续）由任务自己塞进 `note`，加载页按通用样式显示 |
| 预热把 Monaco 常驻渲染进程 | 即使从不打开脚本页，也多占一块渲染进程堆内存 |
| 预热的收益没有量化 | 受限环境里跑不起 `yarn dev`（esbuild `spawn EPERM`），首开耗时的观感只能由使用者冒烟确认。预热带走的是「下载 + 求值」那一半；第一次创建编辑器时 worker 里 TypeScript 语言服务的启动仍要付 |
