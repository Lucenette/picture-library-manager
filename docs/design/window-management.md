# 窗口管理

**状态**：现行架构
**最后更新**：2026-09-26

---

## 1. 背景

这一套不是一次设计出来的，是被几个实测问题推出来的：

1. **一个窗口 = 一个渲染进程。** 开发态实测，从 `new BrowserWindow` 到首帧要 230ms 左右，且与窗口的
   类型、大小、内容多少无关（主窗口 427ms）。窗口的打开频率因此成了"要不要复用"的唯一判据。
2. **窗口先可见，合成器才画第一帧。** 这段时间里用户看到的是窗口自身的样子：文档默认白底、body
   默认边距、溢出自动——于是出现"先白屏、再冒出滚动条、最后才变深色"。
3. **子窗口会先渲染出主界面的导航骨架。** vue-router 的首次导航是异步的，挂载那一刻
   `route.path` 还是初始的 `/`，`App.vue` 据此判定"这不是弹窗"。
4. **按需加载会让时序反转。** 组件挂载晚于 `did-finish-load` 之后，主进程在那一刻推送的弹窗初始
   数据必然丢掉——而且不报错，表现为"弹窗是空的"。第 4 条正是第 1 条的代价：不按需加载，每个
   小弹窗都要把整个应用求值一遍。

## 2. 成本模型：一个窗口 = 一个渲染进程

每个 `BrowserWindow` 都是一个独立的 Chromium 渲染进程。开发态实测，从 `new BrowserWindow` 到首帧：

| 窗口 | 首帧就绪 | 文档加载完成 |
|---|---|---|
| 主窗口 | 427ms | 433ms |
| 脚本下拉浮窗 | 236ms | 237ms |
| 图片查看器 / 扫描配置 / 批量处理 / 相似图结果 | 229–245ms | 231–248ms |

**这些数字与窗口的类型、大小、内容多少无关**——连一个只有两行条目的下拉浮窗也是 236ms。也就是说，
成本是「启动一个渲染进程 + 求值整个应用 + 挂载」的固定开销，而不是页面代码的多少（我们自己的页面
代码一共才 27 KB）。

由此得到两条贯穿全篇的准则：

1. **一个窗口值不值得常驻**，看的是它的打开频率，不是它的大小；
2. **降低单次成本的手段**（按需加载、减少第三方体积）对**所有**窗口同时有效。

## 3. 三层结构

| 层 | 位置 | 职责 |
|---|---|---|
| 窗口工厂 | `main/window-manager.ts` | **唯一**创建 `BrowserWindow` 的地方：尺寸、可见性、`webPreferences`、窗口注册表、开发态计时 |
| 窗口的 IPC | `main/dialogs/**` | 每种窗口一个模块：什么时候打开、初始数据从哪来、结果转交给谁 |
| 页面 | `renderer/views/**` | 一条 hash 路由对应一个页面，只做界面 |

主进程只认两样东西：窗口 id（`'main'` / `'confirm'` / `'popup'` …）与路由字符串（`'/confirm'` / `'/popup'` …）。

注册表同时持有**退出判据**：主窗口是应用的生命周期锚点，`createMain()` 在它的 `closed` 处理器里调
`closeAll()` 关掉其余窗口，`window-all-closed` 随之触发、应用退出。**"最后一个窗口关闭"必须真的等价于
"主窗口关闭"**——浮窗宿主常驻不销毁，一旦它漏在 `closeAll()` 之外，进程就会带着一个看不见的窗口挂住，
并且占着单实例锁：用户再点图标不会有任何反应。

## 4. 单个渲染进程入口

所有窗口共用同一份 `index.html` 与 `main.ts`，靠 hash 路由区分身份；`App.vue` 用 `POPUP_ROUTES`
决定要不要套主界面的导航骨架。两条不变量：

- **除加载页外，路由组件一律动态导入。** 静态导入意味着任何一个小弹窗都要把整个应用（含主界面六个
  页面）求值一遍：每个窗口的公共开销会从 7 个模块 / 27 KB 涨到 26 个 / 133 KB。
- **挂载前必须 `await router.isReady()`。** vue-router 的首次导航是异步的，提前挂载时 `App.vue`
  拿到的 `route.path` 还是初始的 `/`，子窗口会先按「主界面」渲染出导航栏再切换——肉眼可见的一帧。

## 5. 可见性分三档

| 档 | 用于 | 做法 | 为什么 |
|---|---|---|---|
| 立即显示 | 主窗口 | 默认（不传 `visible`） | 启动要尽早出现；空白深色框本来就是正常观感，紧接着就有加载页 |
| 首帧就绪后显示 | 图片查看器、相似图结果 | `showWhenReady: true` | 一次性窗口。窗口先可见、合成器还没画第一帧时，用户看到的是个空白浅色框，比晚一两百毫秒才出现更难受 |
| 建好即隐藏 | 仿原生浮窗宿主 | `visible: false`，何时显示由主进程 `show()` / `hide()` 掌握 | 复用型窗口，见第 9 节 |

## 6. 首帧底色由窗口自己带来

底色不能写死在文档里：主进程建 URL 时把**该窗口自己的** `backgroundColor` 作为查询参数带上
（`getRouteUrl(route, background)` → `?bg=%232b2d30`），`index.html` 用 `var(--win-bg, #1e1f22)`
当文档背景。理由有两个：下拉浮窗是 `#2b2d30`、图片查看器是 `#0d0d0d`，写死会让它们首帧闪一下
别的颜色；而且主题一改，写死的值就过期了。

**这段样式必须内联在 `index.html` 里。** 外链 CSS 与组件样式都晚于首次绘制，而路由又是按需加载的；
少了它，小窗口会先闪白底 → 冒出滚动条 → 才变成深色。它同时定死 `margin: 0` 与 `overflow: hidden`：
各页面自己的滚动由组件内部的滚动容器负责（如 `.app-main` 的 `overflow-y`），文档级滚动只会带来闪现。

## 7. 自绘标题栏

主窗口（`createMain()` 传 `titleBar: { height, color }`）没有系统画的标题栏：它和应用自己的界面重复，
留一条多余的灰条只是丑。**系统窗口按钮保留**，但来源分平台：

| 平台 | 靠什么 | 说明 |
|---|---|---|
| Windows / Linux | `titleBarOverlay`（Window Controls Overlay） | `titleBarStyle: 'hidden'` + overlay，系统把最小化 / 最大化 / 关闭画在我们顶栏的右上角。**不加 overlay 就是一个窗口按钮都没有** |
| macOS | 原生红绿灯 | `titleBarStyle: 'hidden'` 去掉标题栏但保留左上角红绿灯；overlay 在 macOS 上没用（代码按 `process.platform` 跳过）。**那边标题栏不放图标**——左端是系统的，让给红绿灯 |

标题栏是**单独一条**（`App.vue` 的 `.title-bar`，40px），不是把导航当标题栏用：
导航在它下面**左侧**一条 40px 的竖栏里（`.app-rail`），内容区在右。Windows / Linux 的最左边是 40×40 的图标槽（图标 16×16 居中），
**macOS 上不画这个槽**——那一段归红绿灯，标题文字往后让。三处约束，缺一个都是肉眼可见的坏掉：

- **`.title-bar` 是拖拽区**（`app-region: drag`），左侧导航栏不是——导航项是控件，点它该切页而不是拖窗。
  所以标题栏里不要放可点元素；真要放，得给它们补 `no-drag`，否则表现为「点不动」。
- **`--title-bar-height`（CSS）必须等于 `titleBar.height`（主进程）**：系统按钮在这一段里垂直居中，
  对不上就会偏高或偏低；**`titleBar.color` 还要等于 `.title-bar` 的底色**（现在都是 `#26282c`），
  否则 Windows 上按钮那段的底色会和标题栏对不上。
- **系统按钮占的位置要自己让出来**：Windows / Linux 用 WCO 注入的 `env(titlebar-area-x)` /
  `env(titlebar-area-width)` 算左右内边距（按钮可能在左也可能在右，取决于 RTL 与用户设置）；
  macOS 没有这些变量，由 `html.platform-mac` 给标题文字补 78px 左内边距，让开红绿灯。

**失焦要一起变灰。** 窗口不聚焦时，标题栏里的内容压暗（图标与标题文字；macOS 上只有文字，渲染进程挂上 `html.window-blurred`，
由 DOM 的 focus / blur 切换），系统窗口按钮同步换字形色（主进程 `setTitleBarOverlay({ symbolColor })`，
只有 Windows / Linux 有这个接口）。macOS 的红绿灯本来就会随焦点变灰，不需要我们动手。
两端挂的是同一个窗口焦点事件，所以不会出现"按钮灰了文字没灰"这种各说各话的情况。

**Linux 上还有一层前提**：WCO 与圆角都属于客户端装饰（CSD），得桌面环境支持；个别 WM 下系统按钮可能
不画出来（那时窗口只能靠 Alt+F4 / 快捷键关）。真遇到了就要在渲染进程兜底自绘三个按钮——
判据是 `navigator.windowControlsOverlay?.visible`。

启动阶段的迁移页也在主窗口里，所以它同样有标题栏（只是没有左侧导航栏）：迁移跑到一半时窗口照样能拖。

标题栏下面是「左侧 40px 导航栏 + 内容区」两栏（`App.vue` 的 `.app-body`）。导航栏**刻意和标题栏的图标槽
一样是 40px**：那一列从上到下是一条线，看起来才整齐；导航项只有图标，名称走 tooltip。
顺序上，上面四个是数据流页面（来源 → 角色 → 图组 → 图库），**脚本与任务贴底**（任务在最下）——
它们是随时要回来的工具，不该跟流程页面挤在一起。

**失焦时整条 chrome 一起压暗**：标题栏（图标 + 标题文字）与左侧导航栏的图标用的是同一档灰——
它们在视觉上本来就是从左上一路连到左下的一条边。压暗的是图标本身，不是导航栏的底色：
底色一起淡的话，它会和标题栏在接缝处对不齐。

无边框弹窗（`frame: false`）走的是同一条路径，只是它们没有系统按钮：overlay 只在 `!isControl` 时给，
`isControl` 的浮窗宿主（下拉菜单）连这段都不要。**图片查看器仍然是系统标题栏**（`createViewer()` 没传
`frame: false`），这是有意的：它是键盘驱动的工具窗口，不值得为它再造一套顶栏。

## 8. 弹窗的初始数据：挂载后自己去取

主进程**不**在 `did-finish-load` 时把初始数据推给弹窗，而是把数据按渲染进程 id 暂存，等页面挂载后
`invoke(*_INIT)` 来取。

原因是时序：路由按需加载之后，组件挂载会晚于 `did-finish-load`，那一刻推送已经错过——弹窗会是空的，
而且不报错。改成「自己去取」之后，无论组件挂载多晚都能拿到数据。

新增弹窗照 `main/dialogs/confirm.ts` 与 `views/dialogs/ConfirmDialog.vue` 这一对写：主进程一个
`pending` Map 加 `ipcMain.handle(*_INIT)`，页面在 `onMounted` 里 `await invoke`。

## 9. 仿原生浮窗：一个窗口服务全部浮窗

下拉菜单、以后的右键菜单之类「贴在某控件旁边、点别处就收起」的浮窗，**共用一个常驻隐藏窗口**：

| 部件 | 位置 |
|---|---|
| 窗口 | id `'popup'`、路由 `'/popup'`、`visible: false`、失焦即 `hide()`（`window-manager.ensurePopup()`） |
| 页面 | `views/popups/PopupHost.vue`，按推来的 `payload.kind` 从 `COMPONENTS` 里选组件渲染 |
| 通道 | `POPUP_SHOW`（每次展开推内容）、`POPUP_STATE`（宿主挂载时补齐）、`POPUP_HIDE` |
| 预建 | `main/index.ts` 在主窗口起来后调 `warmPopup()`，把渲染进程的启动挪到用户看不见的时候 |

**能这样复用，是因为同一时刻只可能有一个浮窗可见。** 于是「每种浮窗一份常驻渲染进程」变成一份。

约束：

- **内容组件只接收 `payload` prop、只发结果 invoke**，不负责自己的显示与隐藏——可见性归主进程。
- **浮窗不能被渲染进程销毁**：收起用 `POPUP_HIDE`，不要 `window.close()`；失焦由主进程 `hide()`。
  组件实例会被反复赋上新的 payload，所以需要跟着 payload 做一次的副作用（例如把焦点拿回来，否则
  Esc 收不到按键）要放在 `watch(payload)` 里，不能只在 `onMounted` 里做一次。
- **新增一种浮窗改四处**：`@common` 的 `PopupKind` / `PopupShowData` 加一个分支；`PopupHost` 的
  `COMPONENTS` 登记组件；新建内容组件；主进程加一个算坐标并调 `showPopup()` 的模块。
  **窗口、路由、通道都不用动。**

## 10. 改动时的检查点

| 要动的东西 | 同时要改 |
|---|---|
| 新增一个窗口 | `window-manager.ts` 加工厂 → `dialogs/<name>.ts` 注册 IPC 并在 `dialogs/index.ts` 挂上 → `renderer/main.ts` 加路由 → `App.vue` 的 `POPUP_ROUTES` 加路径（若它不套导航骨架） |
| 新增一种浮窗 | 见第 9 节四处 |
| 改主窗口顶栏（高度 / 拖拽区） | `App.vue` 的 `.app-header` 与 `createMain()` 的 `titleBarHeight` 必须相等；顶栏里新增可点元素要补 `no-drag` |
| 新增一个**常驻**窗口（不随主窗口关闭而消失） | 确认 `createMain()` 的 `closed` → `closeAll()` 覆盖到它；漏掉的表现是「关窗后进程不退出」，且单实例锁被占、再点图标毫无反应 |
| 改「哪些路由不套骨架」 | `App.vue` 的 `POPUP_ROUTES` 与 `renderer/main.ts` 的路由表必须一致 |
| 新增启动阶段的页面 | 必须静态导入（它是第一帧），并放进 `POPUP_ROUTES` |

## 11. 已知取舍

- **浮窗宿主常驻一份渲染进程**（约 100 MB 量级），换来点开即出现。判据是「高频 + 轻量」；低频的
  一次性窗口（图片查看器、各确认框）不池化——给它们各留一份常驻进程是白扔内存。
- **单次成本的大头是 Element Plus**（878 KB JS + 349 KB CSS，占每个窗口成本的九成以上）。按组件引入
  能整体压缩，但需要构建期的 `unplugin-vue-components`。
- **开发态每个窗口都会自动打开一个 detached DevTools**，这是使用者的开发习惯，不是性能疏忽：
  不要当成「窗口慢」的原因删掉，它只在开发态生效。
- 若浮窗点开后仍能看出「先空一两帧、再出现内容」，可以再加一步：渲染进程画好后回一个 ack，
  主进程收到才 `show()`。代价是出现时间晚几毫秒。
