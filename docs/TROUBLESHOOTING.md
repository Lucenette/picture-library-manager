# 疑难排查

按现象查。每条都给出「怎么确认」和「根因在哪」。

---

## 扫描 / 任务

### 任务跑着的时候窗口拖不动

**根因**：主进程主线程被同步 CPU 占住。浏览器进程一忙，窗口消息就没人处理。

**现在不应该再出现**——图片解码已迁移到 `worker_threads`。如果仍然卡：

1. 看「任务管理」页里该任务的错误栏有没有 `缩略图工作线程...` 字样。有的话说明线程池没起来，扫描在退化的路径上跑。
2. 主进程控制台（运行 `yarn dev` 的终端）里找 `缩略图工作线程启动失败` 一类的日志。
3. 相关代码：`src/main/image/thumbnail-pool.ts`、`src/main/image/walk.ts`（遍历的分片让出）。

### 点暂停 / 强制结束后没有立刻停

**这是设计。** 暂停与取消是**协作式**的：runner 在「处理完一张图」的边界检查状态，正在执行的整图解码无法中途打断。

所以延迟上限 ≈ 一张大图的解码时间（4K JPEG 通常几百毫秒）。粒度由 `ThumbnailPool.concurrency` 决定，见 `src/main/task/runners/scan.ts`。

强制结束会**立刻**把状态置为「已取消」并释放队列，只是后台还有一张图在收尾——不会留下半成品，因为写库是最后一步且同步完成。

### 任务卡在「生成缩略图 N/M」不动，或日志里出现「缩略图处理超时」

修复过两轮，两个原因都值得知道：

**原因一：死线程被回收。** 工作线程异常退出后，池子曾把它当空闲线程继续派活，
而给已退出的线程 postMessage 不会有任何回复，等待它的请求就永久挂住。
现在死线程一旦 `error`/`exit` 就移出池子并补位，连续补位失败会明确报错。

**原因二（更隐蔽）：并发解码把内存吃穿。** 解码一张图要按「宽 × 高 × 4」分配 RGBA
缓冲区，**与文件体积无关**——实测一个 7.6 MB 的 JPEG 是 11520×8640，需要 380 MB；
三个这样的文件同时解码，瞬时需求超过 1 GB，系统开始换页，单张解码从 10 秒恶化到
几分钟，于是撞上超时。现在调度改为按内存预算分批（见
`src/main/task/runners/scan.ts` 的 `DECODE_MEMORY_BUDGET_BYTES`）：

- 普通图片（1080p / 4K）照旧 4 张并发
- 8K 级别退到 2 张并发
- 一亿像素级的大图独占一批

另外，解码过大幅图片的工作线程会被主动结束并重建，因为解码留下的内存碎片不会及时
归还给系统。

**排查时看两处：**

- 「任务管理」页里该任务的错误栏与结果摘要（`缩略图失败 N`）
- 主进程控制台的 `缩略图生成失败：<路径>` 日志

拿到路径后可以自己量一下尺寸：

```bash
node -e "console.log(require('image-size')('<文件路径>'))"
```

如果像素数远大于预期，就是内存预算该调小；如果扫描仍然慢，看
`DECODE_MEMORY_BUDGET_BYTES` 是不是过于保守。

**根治办法：装 sharp。** 纯 JS 解码器无论如何都要先铺开整图，而 sharp（libvips）按需缩放解码，
内存与耗时都低一个数量级，并且跨平台：

```bash
yarn add sharp
```

装完不需要改任何配置，下一次扫描就会自动切换。任务结果里会显示 `解码 sharp`；
如果显示 `解码 内置`，说明 sharp 没装上或加载失败，日志里会有原因。

### 任务一直停在「进行中」

- 先确认不是「正在解码一张超大图」。
- 任务页的进度与耗时每秒刷新；如果长时间不动，看主进程控制台有没有未捕获异常。
- 应用正常退出时，进行中的任务会被标记为「已取消（应用退出）」；崩溃则会标记为「失败（任务中断）」。

### 扫描报错「脚本未导出方法：identify-structure」

扫描配置里选的脚本没有导出 `identify-structure`。到「脚本管理」页看该脚本的**类型标签**，空的就说明检测不到可用导出。

## 缩略图 / 图片

### 大图没有缩略图

**不应该发生**：任何尺寸的图片都会尝试生成缩略图。

只有在两种情况下会没有缩略图：格式不在解码器覆盖范围（见下一条），
或者这张图解码时工作线程异常（会打印 `缩略图生成失败：<路径>`，可在任务页看到失败张数）。

### 缩略图位置是一个 🖼 占位符

**这些格式只收录元数据、不生成缩略图**：WEBP、AVIF、SVG、ICO。

解码器只覆盖 JPEG / PNG / GIF / BMP / TIFF（见 `src/main/image/thumbnail-decode.ts`）。文件仍会被扫描入库、参与选图与导出，只是没有预览图。

### 图片查看器里大图空白，但底部缩略图正常

缩略图是 `data:` URL，不受同源策略约束；**大图走 `file://`，会被拦**。

开发态页面来自 `http://localhost` 而图片是 `file://`，必须放宽同源策略。检查 `src/main/window-manager.ts` 的 `createWebPreferences()`：

```ts
webSecurity: app.isPackaged,   // 开发态 false（放宽），打包后 true（恢复）
```

写反过一次，表现就是缩略图正常、大图空白。

### 扫描完角色名不对

角色名由 `identify-structure` / `identify-character` 决定。两种处理方式：

- 少量错误：到「角色确认」页重命名。
- 规则不对：改脚本，然后重新扫描该图库。

## 数据

### 数据库在哪

| 运行方式 | 路径 |
|---|---|
| 开发（`yarn dev`） | `dist/data/picture-lib.db` |
| 打包后 | exe 同级的 `data/picture-lib.db` |

同目录下可能有 `picture-lib.db.bak`（每 30 秒保留一次的上一版）和 `.tmp`（写入过程中的临时文件，正常情况下不会残留）。

### 想彻底重置

**先退出应用**（数据库是单文件整体覆写，运行时删除会丢数据），再删掉 `picture-lib.db`，然后重新启动。原始图片不受影响。

### 「删除」会删我的图片吗

不会。所有删除操作**只删数据库记录**。导出是唯一的写文件操作。

### 导出时同名文件被覆盖了

导出序号按角色独立计数、**每轮从 0001 重新开始**。导出到同一个目录时，第二轮会覆盖第一轮的同名文件。

规避：换目标目录，或先清理目标目录。

### 库文件变得很大

缩略图以 Base64 存放在 `image_file.thumbnail`，实测占库体积约九成。这是「预览零开销」的代价，属于已知取舍（见 [ARCHITECTURE](./ARCHITECTURE.md) 的关键取舍一节）。

## 开发 / 构建

### `yarn build` 报 `spawn EPERM`

esbuild 需要启动子进程并用命名管道通信。**受限沙箱环境会拒绝这种调用**（不是项目问题）。请在普通终端里执行，或如实记为「构建未验证」。

### 主进程日志在终端里是乱码

Windows 终端默认代码页是 GBK，而 Node 按 UTF-8 输出，于是中文变成
`缂╃暐鍥剧敓鎴愬け璐ワ細` 这样的一串。执行 `chcp 65001` 切到 UTF-8 即可正常显示，
这不影响日志本身的内容。

### `yarn typecheck` 报找不到 `vue-tsc`

它是 devDependency，先 `yarn install`。

### 导入路径检查工具把 `@/image/thumbnail-worker?nodeWorker` 判为「无法解析」

正常。`?nodeWorker` 是 electron-vite 的虚拟模块（`vite:node-worker` 插件生成，产出独立 chunk 并返回 Worker 工厂），磁盘上没有对应文件。检查脚本应跳过带该后缀的导入。

### 每次写文件都提示 `ReplaceFileW EIO (Win32 32)`

有进程正占用该文件——通常是 `yarn dev` 的构建监听或 IDE。稍后重试即可。

### Git 提示 LF 将被替换为 CRLF

仓库已通过 `.gitattributes` 声明 `* text=auto`：库内以 LF 存储，检出时按平台处理。某台机器上仍看到历史文件混用行尾时，执行一次 `git add --renormalize .` 即可。

### 应用启动后没反应 / 点了图标没新窗口

本项目是**单实例**的：第二个实例会把已有窗口唤到前台然后自己退出。检查任务栏是否已有窗口。

## 脚本

### 改了脚本文件，扫描结果没变

脚本源码是**存在数据库里**的，改磁盘文件不会自动同步。到「脚本管理」页点**重载**。每次调用都会重新编译，因此重载后立即生效，无需重启。

### 脚本里的 console.log 在窗口 DevTools 里看不到

脚本运行在主进程，日志在**运行 `yarn dev` 的终端**，不在窗口的 DevTools。

### 脚本里的 `require('./helper')` 报找不到模块

脚本的 `filePath` 是空串，相对路径解析不到同目录文件。只能 `require` `process.cwd()` 下 `node_modules` 里的包。想复用逻辑请写进同一个文件。
