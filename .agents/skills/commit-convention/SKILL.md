# 提交信息规范

## Summary

本仓库的提交信息默认是「**主题概述 + 逐条列出具体改动**」：主题行一句话说清这一笔做了什么，正文用 `- ` 一条条列出改到哪个文件、
哪个函数、哪个数值。最早那批（2026-06-20~22）30 条里 27 条这样写、平均 5 条；后来正文越写越少，最近 20 条有 15 条只剩主题行——
那是漂移，不是规范。这份 skill 把最早那批的写法固定下来，并说明提交这个动作在本仓库怎么做。

硬性约定以 [AGENTS.md](../../../AGENTS.md) 为准：提交信息用中文、形如 `范围：做了什么`、不擅自 `commit` / `push`。

提交信息是给**程序员**看的——可以写文件、表、通道与根因；**面向使用者的变更另写进 `CHANGELOG.md`**（一行一条、使用者视角），
写法见 [gitflow-release](../gitflow-release/SKILL.md) 的「更新日志怎么写」。

## 实测数据

`git log` 全量统计（2026-09-28，104 条提交），按时间分三段：

| 分段 | 有正文 | 其中条目式 | 条目数均值 |
|---|---|---|---|
| **最早 30 条（2026-06-20~22）** | 27 | **27（写正文就一定是条目式）** | **5.0** |
| 中间 30 条 | 24 | 6 | 1.2 |
| 最近 30 条 | 15 | 10 | 1.5 |

- 主题行 5 ~ 49 字，中位数 27，**没有一条以句号结尾**；最早那批 26 条带 `Co-Authored-By` 署名（见「署名」），只出现在 2026-06-20~06-22。
- 结论：**把最早那批当模板**——主题概述 + 条目式正文，一条一个具体改动。单行提交不是惯例，是后来的退化。

## 主题行

三种写法，都取自历史：

```
重构数据库层：SQL常量抽离、外键移除、级联删除、主进程@别名     ← 范围：具体项、具体项
图片查看器缩略图虚拟渲染 + 居中导航                            ← 做了什么 + 做了什么
缩略图系统完整实现                                             ← 直接陈述
```

- **范围取子系统或主题词**（`脚本` / `文档` / `修复` / `重构` / `界面` / `构建` / `刷新`…），并以**正在推进的那一串工作**为准：
  脚本管理这段工作的每一条都用 `脚本：`，不要为其中一小块另起新词——`脚本分组：` 就是反例，它让 `git log --oneline` 里那一串断掉了。
- 列举具体项时用 `、`，跨类事项用 ` + ` 或 `，`：`UI：复选框批量操作、分页组件、Electron菜单移除、Element中文国际化`。
- **写到具体对象**，不写「优化」「完善」「修复若干问题」这类看不出改了什么的空话。
- **不超过 50 字**（中位数 27），**不带句号**，不折行。
- 修复类用 `修复：`，主题行写哪里坏了，根因留给正文：`修复：升级脚本里再开事务会撞 SQLite`。

## 正文条目式

正文是 `- ` 条目，**一条一个具体改动**，写到文件、函数、数值、颜色、行为这一级。条目是最值钱的部分——半年后要查「当时为什么动这个数」，只有它答得上来。

```
- SQL常量独立到 src/main/sql.ts
- 所有表移除外键，改成业务逻辑+事务控制
- deleteGallery 手动五级级联删除
- 主进程 tsconfig/node 加 @/* → src/main/*
- 数据库蛇形→驼峰自动转换
```

```
- 全局暗色主题，灵感来自 IntelliJ IDEA Darcula
- 背景层次：#1e1f22 / #26282c / #2b2d30 / #323438
- 主色 #3871E1，成功 #388555，危险 #C75458
- 脚本加载改用 Electron 原生对话框，支持多文件选择
```

- 条数：大改动 5~10 条（最早那批均值 5.0、最多 9），小改动 1~3 条。
- 一条一行，行宽 100 字以内；不要把一段话塞进一个超长条目。
- 顺序按「数据/接口 → 逻辑 → 界面」或改动发生的顺序，不按重要性排。
- 为什么与影响面（不变量、代价、迁移影响）写在条目里，不替代条目；一遍就能读懂的改动不必给每条配解释。
- **可以不写正文的唯一情形**：改动只有一处、且主题行已经把它说完整了。到了「无可列」时才空着。

## 修复类

先一段说清症状与根因（说不清根因的修复不要提交），再列改法。示意（病灶段取自 `57fe125`，条目按它的改法整理）：

```
postups 调 renameScript()（它自己用 beginBatch/BEGIN 保证原子），而那时引擎已经开好迁移事务，
SQLite 直接报 cannot start a transaction within a transaction。

- runInMigrationTransaction() 与 beginBatch/endBatch 共用 batchDepth，内层退化成嵌套。
- 升级停在第 5/5 步时账本里那行是 failed 而不是 executed，所以重启即从 postups 继续。
```

顺带说清**修复的边界**：修到哪一步、下一笔要做什么。

## 措辞与格式

- **提交信息是纯文本，不要用 Markdown 标记**：不加反引号、不用 `**` 加粗、不写 `#` 标题、不用链接语法、不写代码块与表格。文件名、函数、命令直接写，不要包反引号——`git log` 与各类工具都不渲染它。
- 全中文、全角标点；颜色值原样写。正文的 `- ` 条目前缀保留：它是纯文本约定，不算 Markdown 标记。
- 直接从改动本身说起，不用「本次提交」「本改动」开头。
- 不复述代码、不自我表扬、不加生成器标记。
- 涉及取舍时写清「决定了什么 + 代价」：`内置脚本没有删除入口，文件只可能被手动删掉，因此不在启动时重建。`
- 出现的数字要有当次实测出处（`实测 3000 行 6ms`），不写估计值。

## 署名

不写署名——不加 `Co-Authored-By`、`Signed-off-by`，也不加生成器标记。最早那批 26 条（2026-06-20~06-22）末尾曾带一行
`Co-Authored-By: DeepSeek <noreply@anthropic.com>`，那是历史，不再沿用。

## 提交这个动作

- **只在被明确要求时提交，绝不 `push`**——推送交给使用者；发布流程见 [gitflow-release](../gitflow-release/SKILL.md)。
- 提交前：跑 [AGENTS.md](../../../AGENTS.md)「改完必须自检」里与本次改动相关的检查，并用 `git status --porcelain` 看清将提交什么
  （临时脚本、`dist/` 产物、测试数据不入库）。
- **中文信息不要用 `git commit -m` 拼**：Windows 命令行按代码页处理参数，中文可能变成乱码。把信息写进临时文件
  （如 `dist/commit-msg.txt`，`dist/` 已被忽略）再 `git commit -F <文件>`，提交后用 `git log -1 --format=%B` 回读核对，最后删掉它。
- 只改信息用 `git commit --amend -F <文件>`；**未推送**时才是安全的。

## 交稿前自检

- [ ] 主题行一句话说清做了什么，范围词与这一串工作一致，不超过 50 字、无句号
- [ ] 全文没有 Markdown 标记（反引号、星号加粗、井号标题、链接语法），正文只保留 `- ` 条目前缀
- [ ] 正文是 `- ` 条目，一条一个具体改动；确实只有一处时才允许空着
- [ ] 条目里出现的文件、函数、数值、颜色都能对上代码或实测
- [ ] 修复类写了症状与根因，不只是「改了哪里」
- [ ] `git log -1 --format=%B` 回读无乱码、无多余空行；之后 `git status --porcelain` 为空
