# 路线图条目落地

## Summary

把 `docs/roadmap/` 里的一条需求做成能合的代码。本文管的是**这条流水线的顺序与判据**：从选条目到落地后的文档收尾。
硬性代码与目录约定一律以 [AGENTS.md](../../../AGENTS.md) 为准，本文不重抄；文档写法见
[doc-convention](../doc-convention/SKILL.md)，提交信息见 [commit-convention](../commit-convention/SKILL.md)，
动到库结构见 [db-maintenance](../db-maintenance/SKILL.md)，发布见 [gitflow-release](../gitflow-release/SKILL.md)。

## 标准流程

1. 选条目（见下），读它的正文，把「待决事项」里还没定的点一次性问清。
2. 核现状（见下）：把「这件事今天成不成立」逐条实测出来，这一步的产出就是方案的背景。
3. 给方案并等答复（AGENTS 的「动手前的边界」；必须停下来问的四类情况见第 5 条）。
4. 写或改 `docs/roadmap/<功能>.md`，并登记 `docs/roadmap/README.md` 的事项表。
5. 方案敲定即开工，**连续推进到整条需求做完**：每一笔都走同一个闭环——写代码 → 跑该笔相关的自检 → 提交（本地），
   一笔不绿不进入下一笔。只有四种情况停下来问：新增 / 移动 / 改名文件或目录、要动 `package.json`、要加依赖、
   方案被实测证伪。
6. 提交，不 push。
7. 收尾：roadmap 迁 design、索引、CHANGELOG 与常驻文档（见下）。

## 选条目

- **状态取值决定能不能开工**：待评审＝方案未定，先把待决事项谈完；待实施＝可直接动手；进行中＝先读文件里记的进度，
  别重复做已完成的部分；已实施＝不要重做。
- **计划版本必须等于当前版本**：`develop` 的 `package.json` 版本号就是下一次 release 的版本号。
  条目排在哪一版**由使用者定**，不要自己往后放——排错版本等于返工。
- 表里写的是「当前排序，不是承诺」：顺序可以商量，版本不能自作主张。

## 先核现状：实测，不照着文档做

文档会过时甚至与代码相反，照着做常会做出多余的东西。开工前查清三件事：

1. **这件事今天成不成立**：读模块、grep 调用点、量条数与体积。三种结果与对策——
   - 已经成立：只做缺的那一半（例：脚本「外部改动后运行生效」早就成立，缺的是类型索引与编辑器同步）；
   - 文档与代码相反：按代码写方案，顺手登记偏差，必要时改文档；
   - 确实没做：正常推进。
2. **数字要有当次出处**：文件数、调用点数、行号、体积。写进方案的背景，不沿用旧文档里的数字。
3. **顺带发现的缺陷**：单立一笔（可独立回滚）或登记 `docs/todo/`，不要混进本笔。

## 方案要写到的六件事

1. **边界**：这层管什么、不管什么、为什么。没有边界的「统一」会被理解成「什么都塞进来」。
2. **不变量**：新机制必须守住的东西，逐条写；落地后它们进设计文档。
3. **失败策略**：什么情况退回默认、什么情况保持现状、什么情况必须报错可见。三者混着含糊过去，实现时必然走偏。
4. **机械守卫**：每条不变量尽量配一个能自动拦住的检查（ESLint 规则、扫描用例、契约用例）——颜色只能走令牌、
   导出符号必须有 JSDoc 都是这么拦的。做不到机械化的，**写明只能人工冒烟**，不要假装有守卫。
5. **依赖决策**：判据是「能不能少写一堆要自己维护的东西」，不是「能不能不加依赖」；定了之后按 AGENTS 的
   「依赖分区」决定进 `dependencies` 还是 `devDependencies`，安装命令交给使用者执行。
6. **分层**：机制统一、策略本地——公共机制只有一处，各消费者只写自己的回调（对照主题管理器 + 注册处理器、
   加载服务 + 任务登记）。不要给每个消费者各写一半。

## 提交怎么切

- 一笔一个**可独立验证**的单元，默认顺序：**公共机制 → 迁移既有调用点 → 消费者 / 界面**。前两类不含界面行为的先合。
- 主题行的范围词要与这一串工作一致，正文一条一个具体改动（见 [commit-convention](../commit-convention/SKILL.md)）。
- **逐笔可验**：切完之后逐个 `git checkout <短哈希>` 跑一遍自检，确认每一笔单独成立——「只有最后一笔是绿的」不算完成。
- 只提交，不 push。

## 自检与验证

- 七项自检见 AGENTS 的「改完必须自检」；改到 `.vue` 就必须跑 `vue-tsc`（`tsc` 看不见 `.vue`）。
- 测试覆盖判据见 AGENTS 的「测试覆盖规则」：能在一个没有 Electron、没有 DOM 的环境里 import 并驱动的，必须有断言。
- 判据之外的（真实窗口、原生解码、真实文件系统副作用）走人工冒烟，且**冒烟清单要具体到窗口与页面**：
  本仓有四个渲染入口（主窗口、弹窗、查看器、浮窗）与七个主页面。
- 回复里分清「已验证」与「需要使用者手动冒烟」——静态检查通过不等于功能正常。

## 落地后的收尾

1. roadmap 文件：状态改 `已实施（提交 <短哈希>）`，再 `git mv` 到 `docs/design/`（写法见 [doc-convention](../doc-convention/SKILL.md)），
   两处 README 索引同步。
2. `CHANGELOG.md` 顶部的未发布段补条目（使用者视角，一行一条）。
3. 常驻文档按需同步：`README.md`（功能 / 技术栈 / 目录树）、`docs/ARCHITECTURE.md`（结构或数据流真的变了才动）、
   `AGENTS.md`（约定变了才动，注意字数预算）。
4. 清账：`docs/todo/` 里被这一笔解决掉的条目，删掉或改成现状。

## 交稿前的自检

- [ ] 条目的计划版本与 `package.json` 的当前版本一致
- [ ] 方案里的每个数字都有当次实测出处
- [ ] 六件事齐了：边界、不变量、失败策略、机械守卫、依赖决策、分层
- [ ] 每条不变量都有机械守卫，或写明只能人工冒烟
- [ ] 新增 / 移动文件与依赖改动的命令都给过使用者并拿到答复
- [ ] 每一笔都走完「写 → 自检 → 提交」的闭环，并单独跑过自检（逐笔 `checkout` 验过）
- [ ] 方案敲定后是一路做完的：中途只在四种情况下停过（新增 / 移动 / 改名文件、动 `package.json`、加依赖、方案被证伪）
- [ ] roadmap 索引、CHANGELOG、README / ARCHITECTURE / AGENTS 的同步点都过了一遍
- [ ] 回复里分清「已验证」与「需人工冒烟」，且没有 `push`
