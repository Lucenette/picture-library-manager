# 文档规范

## Summary

`docs/` 下的每一份 Markdown 只有两种身份：**还没做的方案**与**已经落地的事实**。这份规范说明一份文档属于
哪一态、用哪个模板、写完要动哪些索引，以及落地后怎么 `git mv`。它要达到的效果是：改某个子系统之前，
能先读到它为什么是现在这样、有哪些不变量，而不必翻代码或提交历史。仓库的硬性代码与目录约定见
[AGENTS.md](../../../AGENTS.md)，进程模型与分层见 [docs/ARCHITECTURE.md](../../../docs/ARCHITECTURE.md)。

## 标准流程

1. 读 [docs/README.md](../../../docs/README.md)（各层边界）、[docs/roadmap/README.md](../../../docs/roadmap/README.md) 与
   [docs/design/README.md](../../../docs/design/README.md)，
   再看一份同类现成文档。以文件和索引表为准，不要凭记忆套格式。
2. 判定种类（见下表），打开对应模板，按骨架写。
3. 依次落笔：状态块 → `## 1. 背景` → `### 1.1 修改历史` → 正文。
4. 登记索引：路线图进「事项」表，设计说明进「主题」表。
5. 功能落地后按「落地后的迁移」搬文件、改状态、同步两处索引。
6. 按「交稿前的自检」过一遍再交。

## 文档种类与模板

| 文档要说的 | 位置 | 模板 |
|---|---|---|
| 尚未实施或正在实施的功能方案 | `docs/roadmap/<功能>.md` | [templates/roadmap.md](templates/roadmap.md) |
| 已落地的子系统：为什么这样、有哪些不变量、改动注意什么 | `docs/design/<子系统>.md` | [templates/design.md](templates/design.md) |
| 跨子系统的结构：进程模型、目录归属、数据流 | `docs/ARCHITECTURE.md` | 无模板；结构真的变了才动它 |
| 编码代理的硬性约定与自检步骤 | `AGENTS.md` | 无模板；文档格式规则归本 skill，不要往 AGENTS.md 里加 |

一个功能一个文件，文件名 kebab-case 且与功能同名。`docs/design/` 只接收从路线图迁来的文件，不在那里新写方案。

## 事实：实测，不要假设

文档描述的是代码**今天**的行为，唯一的合格证据是你亲自跑过。

- 写进文档的数字、默认值、报错文案与平台差异都必须有当次实测出处（窗口首帧 427ms 这类数字尤其如此），
  不从别处抄、不凭印象补。
- 复现不了的结论就删掉；依赖外部条件无法验证的，写明「未验证」以及由谁验证。
- 修订旧文档前先读代码、跑命令，而不是读旧文档——过时的说法不会自己暴露。
- 不把「计划做」写成「已经做」；未实施的内容只属于 `docs/roadmap/`。

## 写法规则

- **背景**只回答「什么造成了这份方案」：实测数字、现场症状、约束、不这么做会怎样。3~5 条编号，
  一条一个独立问题，不写「为了提升用户体验」这类没有信息量的结论。
- **修改历史**与背景成对出现，表格三列 `| 日期 | 变更 | 原因 |`。新文档只有一行
  `| <今天> | 首次定稿 | — |`，日期取真实当天日期；每被实质修订一次才补一行，不要预填、不要写编年史。
- **正文写结论**：用 X 就写「这里用 X」。需要记录取舍时，写清决定了什么以及由此产生的后果
  （如 task-process.md 的「设计结论：不引入继承体系」），不要写逐条论证候选方案的辩护段落。
- 不重抄代码已经表达清楚的实现细节；要写的是不变量、边界条件、影响面、已知代价。
- 文件、表、IPC 通道、模块名一律用代码里的写法；路径相对仓库根；行内代码用反引号。
- 设计说明不拿路线图文件当论据；路线图之间只在确有依赖时用 `**关联**` 一行互指。
- 图示用 ASCII 框图（画法见 `docs/ARCHITECTURE.md`），不贴外部图片。
- 全文中文。

## 废料清单

AI 写的文档天然容易膨胀。交稿前拿这几条扫一遍，命中就删：

- **重复的规则**：挑一个有特征的短语在仓库里搜一遍，同一件事只留一处，别处改成链接。
- **越级的历史**：正文只写当前事实；谁在哪一版改的、当时试过什么，归提交信息、[postmortem](../../../docs/postmortem/README.md) 或修改历史表。
- **状态注记**：「已实现」「待做」「以后会……」这类标注会腐烂——目录位置与代码本身才是状态的权威。
- **手抄的清单**：源码或生成物已经是权威的目录、IPC 通道、测试与包清单，不要在文档里再列一遍。
- **推理过程**：一步步的实现叙述、显而易见的证明、测试走查、被否决的局部方案；只留结论与它约束了什么。

## 落地后的迁移

1. 路线图文件的状态改成 `已实施（提交 <短哈希>）`。
2. `git mv docs/roadmap/<功能>.md docs/design/<子系统>.md`——不重写、不删除，历史留给 git。
3. 从 `docs/roadmap/README.md` 的「事项」表删掉该行，往 `docs/design/README.md` 的「主题」表加一行。
4. 开头块换成设计说明形态：状态行改 `**状态**：现行架构`，补 `**最后更新**：<今天>`；原先没有
   `### 1.1 修改历史` 的补上（迁移本身不算修订，除非同时改了内容）。
5. 正文按事实修订：把「将要做」改成「现在是这样」，删掉实施期间的临时说明。
6. 只有跨子系统结构真的变了，才动 `docs/ARCHITECTURE.md`。

## 交稿前的自检

- [ ] 种类正确：未实施的没混进 `design/`，已落地的没留在 `roadmap/`
- [ ] 状态块齐全，`**状态**` 取值出自 roadmap README 的状态取值表
- [ ] 背景与修改历史成对，新文档的历史只有一行，日期真实
- [ ] 两处 README 索引与实际文件一致，链接点得开
- [ ] 正文没有复述代码，没有候选方案辩护
- [ ] 过了一遍「废料清单」：没有重复规则、越级历史、状态注记、手抄清单与推理过程
- [ ] 没有占位符残留，行内代码都是反引号
- [ ] 跑过 `node scripts/check-docs.mjs`：编码、链接、锚点、索引与 frontmatter 都过
