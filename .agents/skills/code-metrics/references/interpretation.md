# 数字怎么读

这份文件只说一件事：把 `count-lines.mjs` 的输出变成一句关于**规模与结构**的判断。
统计口径、命令与自检在 [SKILL.md](../SKILL.md)；这里不回答「项目健康度如何」——
测试、CI、依赖、协作基建都不是代码量能推出来的，不属于这个 skill。

## 规模档位

用**代码行**对档位，不要用总行数——总行数被空行与注释撑起来，跨项目不可比。

| 档位 | 大致代码行 | 说明 |
|---|---|---|
| 玩具 / 单文件脚本 | <1k | 无分层，一个文件跑完 |
| 小工具 | 1k–10k | 有目录划分，通常无测试、无 CI |
| 中型独立应用 | 10k–50k | 有分层与构建流程，可维护的独立产品 |
| 大型应用 | 50k–200k | 多子系统、有团队协作痕迹 |
| 平台级 | >200k | VS Code、Chromium 一类 |

档位只描述**体量**，不构成评价：10k 行的认真项目强过 100k 行的失修项目。
报数时说「约 11.5k 行代码，落在中型独立应用的下沿」比单说「11536 行」更有用。

## 文件粒度分布

平均值会被一个超大文件拉走，**看分布与单文件 Top，不要只看平均**。

- **≤50 行的文件占比高** → 拆分细，改动面容易控制。
- **>500 行的文件要逐个看内容**，只看行数会误判。本仓库实测三个例子（提交 `571751b`）：
  `ScriptPage.vue` 874 行里脚本占 823 行、模板只有 28 行，是真正的逻辑集中，该拆；
  `types.ts` 564 行里是 66 处 `type` / `interface` 声明、0 个函数，属于声明堆；
  `db.ts` 894 行里是 80 个 `export function`（SQL 在隔壁 `src/main/database/sql.ts`），平均 7 行一个，是薄封装聚合。
  三者行数接近，处置方式完全不同——后两个不该按行数动。
- **居中的一堆（200–500 行）** 才是最值得留意的区间：既没有拆开，也不是数据堆。

## 会误导人的几处

- **`.vue` 的代码行包含 `<template>` 与 `<style>`**，与 `.ts` 的代码行不是同一种东西，不要混着加总得出「前端比后端大」这类结论。
- **注释率是行首启发式**：整行以 `//`、`/*`、`*`、`*/`、`<!--` 开头才算，行尾注释归代码行，误差量级 ±2%。
  不要拿它做「注释覆盖率必须 ≥ x%」这类阈值判断。
- **`(root)` 那一行指的是统计根本身那一层**，带 `--root` 时不是仓库根；把配置与入口文件算进去是正常的。
- **空行与注释占比高时总行数虚高**：一个 20% 注释的文件，总行数比代码行多出四分之一还多。
- **非代码的行数（Markdown / yml / json）单独成段**，不要并进代码合计里比大小——`.md` 的行数不代表代码量。
  注意 `src/` 下的 `.xml` 是代码（建表 SQL 的版本化正文），别按扩展名把它排除掉。
