# 基准测试

性能敏感的**纯函数**放这里压住：排序键、相似分组的比对都随规模增长，改动它们时先看这里的数字，别只看「测试通过」。

## 怎么跑

```bash
yarn bench
```

只跑一个文件就在末尾带路径：`yarn bench benchmarks/sort-key.bench.ts`。

Vitest 5 移除了内置的 bench API，所以基准写成普通 `test`：计时在 [harness.ts](./harness.ts)（`node:perf_hooks`，
热身一次后取多轮**中位数**，最快/最慢一并打印用来看抖动）。`vitest.bench.config.ts` 与常规测试分开，
`fileParallelism: false` + `maxWorkers: 1` 保证同一时刻只跑一个基准，墙钟不被别的基准挤。
不进 CI，也不在 CI 的每次 push 上跑。

## 数据从哪来

**全部是合成数据，由本目录里的命名常量造出**，不用真实图库、用户素材或网络。
这不是偷懒：真实数据不可复现、会随使用者变化，做不了同机前后对比。
代价是这些数字只回答「这段代码有没有数量级退化」，回答不了「真实库有多快」——
真实路径（网络盘遍历、sharp 解码、任务调度）属于人工冒烟，基准测不了。

## 工作量与计时边界

| 基准 | 样本（命名常量） | 计时边界 | 参考机中位数 |
|---|---|---|---|
| 排序键 5000 个混合名（默认 profile） | `SAMPLE_COUNT = 5000`；汉字池 16 字、文件号 `% 997`（质数，与 16 互质） | 5000 次 `sortKeyOf`；样本在模块顶层造好，不计时 | 229 ms |
| 排序键 5000 个混合名（姓名 profile） | 同上，改用 `CHARACTER_NAME_PROFILE` | 同上 | 270 ms |
| 相似分组 1000 张图 | `ROW_COUNT = 1000`、`SEED_MODULUS = 500`、`HASH_BITS = 24` | 一次 `buildSimilarGroups`（约 50 万次两两比对） | 22 ms |

参考机：linux x64、Intel i7-6500U（4 线程）、15 GB、Node v24.21.0（2026-10-04 实测）。
换机器这些数字不可比——它只用于**同一台机器上的前后对比**。

## 为什么取中位数而不是最快轮

最快轮只反映机器最好的一瞬间。同一份代码在参考机上实测 7 轮，排序键的最快 186 ms、最慢 364 ms，
取最快轮会给出一个偏乐观且不稳定的数字；中位数才代表常态，最快/最慢则用来判断这次运行可不可信。

## 没有预算，也还没进 CI

现在只有观测值，没有阈值——所以它**拦不住任何东西**。要当门禁，得先补齐：

1. 以一台参考机记录期望值；
2. 实测参考机与 CI runner 的墙钟比，配一个防抖余量（墙钟预算必须在空闲的 runner 上单独跑）；
3. 把预算写成源码里的常量，**环境变量不许覆盖**；
4. 先在 PR 上只发数字不阻塞，攒够历史再收紧。

顺带一句：这个仓库真正的性能风险不在这两个纯函数，而在网络盘上的同步遍历与 sharp 解码，那些靠人工冒烟。
